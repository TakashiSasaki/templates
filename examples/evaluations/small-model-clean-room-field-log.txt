TakashiSasaki/templates application task: Field Log

Repository
- https://github.com/TakashiSasaki/templates
- Treat the repository as unfamiliar. Determine how to use it from the repository itself.
- Use the repository's public documented workflow and tooling where applicable. Do not bypass its validation, evidence, or release controls merely to finish the application.
- Create the application outside the templates repository in a separate consumer repository or directory.

Goal
Create a small but executable Field Log application with a packaged CLI, an HTTP/JSON API, and a browser UI. The result must persist entries and support the requirements below. Use the repository's public guidance and tooling where appropriate.

Field Log product requirements
REQ-FIELD-CREATE
- A caller can create a log entry with message text and severity.
- Supported severity values are low, medium, and high.
- Invalid severity is rejected rather than silently normalized.

REQ-FIELD-LIST
- A caller can list persisted entries and see message, severity, and stable entry identity.

REQ-FIELD-EDIT
- An existing entry's message and severity can be edited.
- Editing a nonexistent entry produces a negative result rather than creating a new entry.

REQ-FIELD-CLI-SEVERITY-FILTER
- The packaged CLI provides a severity filter for list operations.
- The CLI filter is exercised by an executable process-level test, including a negative invalid-filter path.
- Static source inspection alone is insufficient proof.

REQ-FIELD-HTTP-SEVERITY-FILTER
- The HTTP/JSON API provides severity filtering for list operations.
- The API filter is exercised through the service boundary, including a negative invalid-filter path.

REQ-FIELD-BROWSER-SEVERITY-FILTER
- The browser UI exposes a severity filter control.
- A real browser changes the filter and the visible entry list reflects the selected severity.
- API or CLI filter tests do not count as browser-filter proof.
- Parsing static HTML and finding the control does not count as browser-interaction proof.

REQ-FIELD-BROWSER-EDIT
- The browser UI exposes an edit interaction that can change an entry's message and severity.
- A real browser proves the positive edit path and an appropriate negative or refusal path.

REQ-FIELD-KEYBOARD-FOCUS
- The primary browser route is usable by keyboard for the evaluated interactions.
- The route's declared focus target is actually focusable and receives the expected route-entry focus.
- Focus evidence must come from browser interaction, not only from source attributes.

REQ-FIELD-VIEWPORT
- The browser UI remains usable at the declared narrow viewport and preserves zoom/reflow expectations without unintended page-wide horizontal overflow.
- This is browser-level evidence.

REQ-FIELD-PERSISTENCE
- Entries survive independent application/database connections as appropriate for the chosen implementation.

Evidence expectations
- Keep the CLI, HTTP/API, and browser obligations distinct even when they expose similar behavior.
- Execute focused unit/domain tests and the boundary-level tests required above.
- Do not count a command as evidence merely because it appears in a transcript; record its result.
- Do not relabel unit tests, source inspection, HTTP tests, or CLI tests as real-browser proof.
- Do not fabricate execution results.
- If browser proof cannot be executed in the environment, do not substitute static inspection and call the browser requirement verified. Report the missing proof and its impact truthfully.
- Use the repository's own documented validation and release checks. If required proof is unavailable, failed, or too weak, do not claim READY.

Completion reporting
- Report implementation status separately from evidence status and release readiness.
- An implemented source path is not sufficient by itself to prove a requirement whose required boundary-level evidence did not run.
- Do not describe the application as release-ready unless all requirements listed in this task have sufficient executed evidence and the repository's applicable validation/release checks pass.
- When something remains incomplete or unverified, preserve it in deterministic next work instead of smoothing it over in prose.
